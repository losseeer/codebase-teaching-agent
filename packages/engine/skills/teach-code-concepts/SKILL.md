# 讲机制（教学侧）

## 适用范围

用户在代码问答里问「这段为什么这么写 / 这里在干什么 / 换成另一种行不行」，而答案落在**机制层**而不是业务层时取这份。纯业务流程讲解、画架构图/流程图（走可视化那几份）、出题（走 `exercise-code-concepts`）不在范围内。

## 第一步：判主题，只看代码证据

模块名、目录名、注释里的词都不算证据。按命中的标识符与结构判，命中哪个主题就只讲哪个：

| 主题 | 取哪份附属文件 | 命中证据（示例，非穷举） |
| --- | --- | --- |
| 并发、内存、进程与 IO | `os.md` | 线程池构造与拒绝策略、`Lock`/`synchronized`/原子类、`ThreadLocal`、延时队列、信号量、selector/epoll、mmap |
| 传输、协议与序列化 | `cn.md` | socket 与 HTTP 客户端/服务端、连接池参数、超时与重试、TLS 握手、MQ 生产与消费、网关路由、序列化框架 |
| 数据结构与算法 | `ds.md` | 自写容器、比较器、堆/优先队列、LRU/LFU、Trie、跳表、并查集、环形缓冲、二分与归并 |
| 后端工程结构 | `backend.md` | 依赖注入与代理切面、事务边界、缓存读写与失效、幂等与去重、限流熔断、分层与依赖方向、埋点 |

三条规则：

1. **一轮只讲一个主题**。同时命中两个（例如「带锁的 LRU 缓存」）就先讲用户问的那个符号所在的机制，末尾用一句话说明另一层是什么、要不要接着看。
2. **判不出主题就别硬套**。四个都对不上就是业务代码：直接按代码讲数据怎么流、状态怎么改，不要为了套模板编一个「这是典型的 XX 模式」。
3. 主题只决定**该讲哪三件事**和**常见误解**，具体结论仍然必须来自这份仓库的行或静态产物。

## 第二步：按六步讲，一步都不能虚

1. **它在解决什么问题**——用不带术语的一句话（「同一笔订单可能被回调两次，这里挡住重复处理」）。
2. **指到具体行**——`文件:行号`，说清谁调它、它挡住什么。行号只能来自你读过的内容或产物，不能凭印象。
3. **拿掉会怎样**——失败模式要具体到「什么场景下、以什么形式出错」。给不出具体场景的，就别写这一条。
4. **本仓的真实参数与边界**——容量、超时、重试次数、批量大小、默认值：只报你在这份仓库里看到的数字，包括它写在哪个配置文件；配置可能被环境变量覆盖，看到了也要说明这一点。
5. **一个常见误解**——从主题文件里挑与这段代码直接相关的那一条，不要泛泛而谈。
6. **留一个可自查的追问**——让学习者去代码里找一个证据（「看看这个线程池的拒绝策略是谁设的，找不到就说明用的是默认」）。

## 红线

- **不背定义**。教科书式的「XX 是……」不算讲解；每句结论都要能指回这份仓库的某几行或某个产物读数。
- **不虚构**。没读到的参数不说默认值；`read_file` 被截断、`query_facts` 回「这类产物不在册」，就照实说没看到，不要用「通常」「一般来说」补上。
- **静态可达 ≠ 必然执行**。分支可能一辈子不走，写「当……时走到」，不写「系统会……」。
- **不把命名当证据**。`ThreadPoolManager` 里可能什么池都没有；`xxxService` 可能只是个转换器。
- **一次别讲超过一个机制**。学习者记不住两条以上的新概念，宁可下一轮再讲。

## 证据怎么取

1. 有静态产物时先 `query_facts`（类型关系、注册与配置索引能直接告诉你接口背后是哪个实现、字段是什么类型）。
2. `search_code` 定位「这个机制在仓库里还有别的实现吗」，避免只讲一个文件就断言全局。
3. `read_file` 读关键那几十行——参数、条件、异常处理都在正文里。
4. 跨文件的调用关系看上下文里给的调用边/邻接，不要靠猜。

## 要如实交代的限制

反射与动态代理的织入点、依赖注入实际选中的实现、运行时被环境变量或配置中心覆盖的参数、线程调度与真实耗时、异步回调的先后顺序——这些都不在静态证据里。讲到它们时说「这里我只能看到注册处，实际生效值要去配置/运行环境确认」，不要替学习者臆断。
