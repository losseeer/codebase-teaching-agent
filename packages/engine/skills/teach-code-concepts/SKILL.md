# 代码机制讲解

本 Skill 用于回答代码相关的机制问题，例如：

- 这段代码为什么要这样写？
- 这里具体做了什么？
- 如果去掉这段逻辑会有什么影响？
- 换一种实现是否可行？
- 某个参数、判断或数据结构在这里起什么作用？

重点是帮助学习者理解代码背后的机制，而不只是复述代码或介绍相关技术概念。

纯业务流程讲解不属于本 Skill 的重点；需要绘图时使用 `project-visualization`，需要生成练习题时使用 `exercise-code-concepts`。

## 1. 根据问题决定讲解深度

首先判断用户究竟想了解什么，不要把所有问题都变成完整的源码分析。

**概念解释**

当问题针对通用技术概念，或者用户只想知道某个术语的含义时，直接解释：

- 用日常语言说明概念；
- 通过一个最小例子解释其工作方式；
- 必要时说明适用条件或容易混淆的边界。

这类回答不需要进行仓库主题分类，也不需要读取附属知识文件。

如果涉及当前仓库，应明确区分通用概念和项目实际实现。例如：「这是线程池的一般工作机制，当前项目是否采用了这种配置，还需要看具体代码。」

**代码机制分析**

当问题指向具体代码，并且需要解释实现原因、运行机制、约束条件或替代方案时，结合仓库源码展开分析。

用户要求简短时，优先回答最关键的机制，不必展开完整背景。用户要求深入分析时，再补充调用关系、参数、边界和相关知识。

**判断原则：** 讲解深度由问题决定，而不是由 Skill 的章节结构决定。

## 2. 确定代码所属的技术主题

代码机制分析时，根据实际代码证据确定讲解主题，以便选择合适的知识补充材料。

| 主题 | 附属文件 | 典型代码证据 |
| --- | --- | --- |
| 并发、内存、进程与 IO | `os.md` | 线程池及拒绝策略、`Lock`、`synchronized`、原子类、`ThreadLocal`、延时队列、信号量、selector/epoll、mmap |
| 传输、协议与序列化 | `cn.md` | Socket、HTTP 客户端与服务端、连接池、超时与重试、TLS 握手、MQ 生产消费、网关路由、序列化框架 |
| 数据结构与算法 | `ds.md` | 自定义容器、比较器、堆与优先队列、LRU/LFU、Trie、跳表、并查集、环形缓冲区、二分与归并 |
| 后端工程结构 | `backend.md` | 依赖注入、代理与切面、事务边界、缓存读写与失效、幂等与去重、限流熔断、分层与依赖方向、埋点 |

分类遵循以下原则：

1. 以标识符、调用关系和实际代码结构为依据。模块名、目录名和注释中的技术术语不能单独作为分类依据。
2. 一次讲解聚焦一个主题。如果代码同时涉及多个主题，优先解释用户当前关注的机制，其他主题只在理解当前机制确有必要时补充。
3. 四类主题均不匹配时，直接从业务代码入手，解释数据流向和状态变化，不强行归类。
4. 主题分类只决定知识补充方向，不预先决定代码结论。所有项目相关结论都必须有源码或静态分析证据支持。

确定主题后，只有在附属知识文件能为当前问题提供直接帮助时才读取，不需要为了分类而机械加载。

## 3. 围绕问题组织讲解

不采用固定章节数量，也不要求每次回答覆盖所有讲解要素。

根据用户的问题，从以下几个方面选择必要内容，并按照代码的实际执行关系组织起来。

**问题背景**

解释这段代码解决了什么问题。尽量从具体场景切入，而不是先介绍一大段技术定义。

例如：「两个线程可能同时修改同一个计数器，因此这里需要保证更新操作不会相互覆盖。」

如果用户已经明确知道问题背景，就不必重复。

**代码位置与执行过程**

定位关键代码，说明它在整个调用过程中的位置，以及相关变量、方法和条件分支如何共同发挥作用。

需要时给出 `文件:行号`，并说明调用者、被调用者及关键数据如何流转。

不要只罗列代码行，要解释关键语句之间的关系。

**实现机制与设计原因**

围绕用户真正关心的问题解释实现原理。

例如：
- 为什么使用锁，而不是直接使用原子类？
- 为什么先检查缓存，再访问数据库？
- 为什么这里需要维护一个额外的数据结构？
- 为什么要在这个位置进行异常处理？

涉及替代实现时，比较它们在当前代码场景下的差异，而不是泛泛介绍各自的优缺点。

**行为边界与参数**

当参数或边界条件影响机制理解时，补充本仓库能够确认的实际配置，例如容量、超时时间、重试次数、批量大小和默认值。

同时关注特殊输入、并发竞争、异常分支和资源释放等容易被忽略的情况。

如果某个参数与当前问题无关，就不必专门介绍。

**反事实分析**

当用户询问「为什么需要这段代码」或「能否去掉」时，分析移除或替换后的影响。

尽量给出具体触发条件和错误表现，例如：「当两个线程同时处理同一订单时，去掉这段去重逻辑可能导致重复扣款。」

如果无法从代码推导出明确的失败场景，就不要为了说明重要性而虚构后果。

**相关知识与误区**

如果有必要，再补充一个与当前代码直接相关的知识点，帮助理解更深一层的机制。

优先选择附属知识文件中与当前问题相关的内容，不要为了增加知识密度而扩展到无关概念。

**引导自查**

在适合教学的场景中，可以留下一个能够通过阅读当前代码回答的问题，引导学习者自己验证理解。

例如：「这个线程池的拒绝策略在哪里设置？如果没有显式设置，框架实际采用什么策略？」

自查问题是可选的，不需要每次回答都以提问收尾。

## 4. 代码证据的查找顺序

解释机制前，优先利用现有静态分析结果，再回到源码确认细节。

1. **`query_facts`**：查看类型关系、接口注册、配置索引等静态信息，确认接口背后的实现及字段类型。
2. **`search_code`**：搜索仓库中的其他实现，避免只看一个文件就对整个项目下结论。
3. **`read_file`**：阅读关键代码片段，重点检查参数、条件分支和异常处理。
4. **调用关系信息**：需要说明跨文件调用关系时，使用已有的调用边和邻接信息，不根据命名或代码位置自行推断。

根据问题选择必要的证据，不要求每次都完整执行所有步骤。

例如，只问一个局部条件判断的作用时，阅读对应代码可能已经足够；如果要判断某个接口在整个仓库中实际采用了哪种实现，就需要进一步搜索和追踪调用关系。

## 5. 静态证据的边界

有些行为无法仅凭源码和静态分析结果确认，遇到时应明确说明。

主要包括：

- 反射与动态代理的实际织入位置；
- 依赖注入运行时最终选中的实现；
- 环境变量或配置中心覆盖后的参数值；
- 线程调度情况与实际执行耗时；
- 异步回调的真实执行顺序。

例如，源码只能确认某个实现已注册时，应说明：「这里只能看到注册信息，实际注入的是哪个实现，还需要结合运行时配置确认。」

如果 `read_file` 返回内容被截断，或者 `query_facts` 明确提示相关信息不在静态索引中，也应如实说明。

不要用框架惯例或经验猜测来填补证据缺口。能够确认的内容讲清楚，暂时无法确认的内容说明「我推测」。
