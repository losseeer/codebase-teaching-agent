# 讲机制（教学侧）

用户在代码问答里问「这段为什么这么写 / 这里在干什么 / 换成另一种行不行」、答案落在机制层时，按本技能讲。纯业务流程讲解不在范围内；画图走 `project-visualization`，出题走 `exercise-code-concepts`。

## 一、判主题，只认代码证据

模块名、目录名、注释用词不构成证据；按命中的标识符与结构判定，命中哪个主题就只讲哪个：

| 主题 | 附属文件 | 命中证据（示例，非穷举） |
| --- | --- | --- |
| 并发、内存、进程与 IO | `os.md` | 线程池构造与拒绝策略、`Lock`/`synchronized`/原子类、`ThreadLocal`、延时队列、信号量、selector/epoll、mmap |
| 传输、协议与序列化 | `cn.md` | socket 与 HTTP 客户端/服务端、连接池参数、超时与重试、TLS 握手、MQ 生产与消费、网关路由、序列化框架 |
| 数据结构与算法 | `ds.md` | 自写容器、比较器、堆/优先队列、LRU/LFU、Trie、跳表、并查集、环形缓冲、二分与归并 |
| 后端工程结构 | `backend.md` | 依赖注入与代理切面、事务边界、缓存读写与失效、幂等与去重、限流熔断、分层与依赖方向、埋点 |

三条规则：

1. **一轮只讲一个主题**。同时命中两个（例如「带锁的 LRU 缓存」）时，先讲用户所问符号所在的机制，末尾用一句话交代另一层是什么、是否继续。
2. **判定不了就不归类**。四个主题都对不上时按业务代码讲：数据怎么流、状态怎么改；不为套用模板编造「这是典型的 XX 模式」。
3. 主题只决定该讲的三件事与常见误解；具体结论仍必须来自本仓的源码行或静态产物。

## 二、按六步讲

1. **它在解决什么问题**：用不带术语的一句话陈述这段代码挡住的问题（「同一笔订单可能被回调两次，这里挡住重复处理」）。讲问题，不是背定义。
2. **指到具体行**：给出 `文件:行号`，说明谁调用它、它挡住什么。行号只能来自已读过的内容或静态产物。
3. **拿掉会怎样**：失败模式具体到「什么场景下、以什么形式出错」，给不出具体场景就不写这一条。写「当……时走到」，不写「系统会……」。
4. **本仓的真实参数与边界**：容量、超时、重试次数、批量大小、默认值——只报在本仓看到的数字，并注明所在配置文件；配置可能被环境变量覆盖，见到就说明。
5. **一个常见误解**：从主题附属文件里挑与这段代码直接相关的一条，不泛泛而谈。
6. **留一个可自查的追问**：让学习者去代码里找证据（「看看这个线程池的拒绝策略是谁设的，找不到就说明用的是默认」）。

## 三、证据的取用顺序

1. 有静态产物时先 `query_facts`：类型关系与注册、配置索引能直接给出接口背后的实现与字段类型。
2. `search_code` 确认该机制在仓库内是否还有其他实现，避免只读一个文件就断言全局。
3. `read_file` 读关键的几十行：参数、条件、异常处理都在正文里。
4. 跨文件调用关系使用上下文中的调用边与邻接信息，不做推断。

## 四、静态证据给不了什么

反射与动态代理的织入点、依赖注入实际选中的实现、运行时被环境变量或配置中心覆盖的参数、线程调度与真实耗时、异步回调的先后顺序——这些不在静态证据里。讲到时如实说明「这里只能看到注册处，实际生效值要在配置或运行环境确认」。未读到的参数不写默认值；`read_file` 被截断、`query_facts` 回「不在册」时照实说，不用「通常」「一般来说」补足。
