# 传输、协议与序列化（讲法补充）

## 这段代码在工程里通常长什么样

- 出站：HTTP/RPC 客户端封装（统一超时、重试、连接池）、Redis/MQ 客户端配置、序列化框架（JSON/protobuf/Hessian）。
- 入站：路由与参数绑定、拦截器/过滤器、统一响应包装、异常映射。
- 消息：生产者与消费者成对出现，配重试队列/死信队列/幂等表。
- 网关与负载：路由规则、鉴权前置、限流阈值。

## 必须讲清的三件事

1. **一次往返花在哪里**：连接建立、序列化、等待响应、重试。指到设超时与设重试次数的那几行。
2. **契约在哪**：字段名与类型由谁定（DTO、proto、注解、文档），改一边不改另一边会怎样。
3. **不可靠的那一段怎么处理**：超时后是重试还是放弃、重复投递怎么挡、消费失败后消息去哪。

## 常见误解（挑与这段代码直接相关的一条讲）

- 「设了超时就不会卡住」——连接超时与读超时是两个参数，重试还会把总耗时乘起来。
- 重试不等于幂等：没有去重依据的重试会重复扣款、重复发货。
- 序列化框架的默认行为（多态、日期格式、未知字段）各家不同，别按另一家的直觉解释。
- MQ「发了就等于消费了」——至少一次投递意味着重复是常态。
- 连接池上限太小会表现为「下游变慢」而不是「连不上」。
- 网关改了路径不等于后端不用改：两边规则要一起看。

## 追问示例

- 「这个客户端的超时和重试分别在哪两行设的？乘起来最坏情况多久？」
- 「这条消息消费失败之后去了哪里？去找死信队列或重试队列的注册处。」
- 「这个 DTO 的字段名是两边各自定义，还是有一份共同的契约文件？」

## 别讲什么

真实网络延迟、丢包与拥塞行为、TCP 握手细节、TLS 协商结果、服务端实际超时——都看不到。能讲的只有「这份代码把超时设成 X、重试设成 Y，所以最坏等待是两者相乘」这类从行号直接得出的结论。
