# 后端工程结构（讲法补充）

## 这段代码在工程里通常长什么样

- 分层：接口/控制器 → 服务 → 数据访问 → 实体与 DTO；依赖方向应当从外向内。
- 横切：依赖注入、切面（日志、鉴权、限流、熔断）、拦截器、全局异常处理。
- 数据一致性：事务边界、缓存读写与失效、幂等与去重、分布式锁与租约。
- 可运维：健康检查、指标与链路埋点、配置开关、优雅关闭。

## 必须讲清的三件事

1. **责任落在哪一层**：这段做的是校验、编排还是存取；说得出「它知道业务规则吗」。
2. **边界在哪一行开始、哪一行结束**：事务从哪个方法起效、切面套住了哪些方法、缓存读写分别在哪。
3. **出错时谁来兜**：异常被谁捕获、被包装成什么返回给调用方、有没有回滚或补偿。

## 常见误解（挑与这段代码直接相关的一条讲）

- 事务注解加在同类内部方法上通常不生效（代理只拦外部调用），别按「加了注解就有事务」解释。
- 「先更新数据库再删缓存」与「先删缓存再更新数据库」的失败场景不同，讲的时候要指明是哪一种顺序。
- 幂等靠的是去重依据（唯一键、状态机、token），不是「先查一下有没有」。
- 限流阈值配在网关还是应用内，挡住的流量完全不同。
- 缓存命中率低不等于缓存没用；要看它挡的是哪一段开销。
- 分层名字对得上不代表依赖方向对：DTO 被数据访问层引用就是反向依赖。

## 追问示例

- 「这个服务方法上有事务注解吗？如果有，被同类里另一个方法直接调用时还生效吗？」
- 「缓存失效发生在写库之前还是之后？去找那两行的顺序。」
- 「这条链路的异常最终被谁接住？返回给调用方的是 5xx 还是包装后的业务码？」

## 别讲什么

容器实际织入的代理形态、运行时生效的配置值（可能被环境变量或配置中心覆盖）、真实 QPS 与延迟分布、事务隔离级别的实际数据库设置——都不在静态证据里。说清「代码里写的是什么、还有什么看不到」即可。
