# 数据结构与算法（讲法补充）

## 这段代码在工程里通常长什么样

- 标准库容器：`Map`/`List`/`Set`/`Deque`/优先队列，配比较器或哈希键。
- 自写结构：LRU/LFU 缓存、Trie、跳表、并查集、环形缓冲、对象池。
- 算法片段：二分、归并、快排、BFS/DFS、滑动窗口、前缀和。
- 数据形状转换：分组、聚合、扁平化、去重、排序键组合。

## 必须讲清的三件事

1. **为什么选这个结构**：它换来的是哪一次操作变快，代价是什么（内存、写入、有序性丢失）。
2. **复杂度落在真实规模上**：这段处理的是几十条还是几十万条？规模小就别把 O(n log n) 讲成决定因素。
3. **键与比较器的一致性**：`equals`/`hashCode` 是否配套、比较器是否自洽（传递性、与 `equals` 一致）、可变对象当键的后果。

## 常见误解（挑与这段代码直接相关的一条讲）

- 「哈希表比列表快」——小 n 下常数与内存局部性反转结论。
- 用可变对象做 `Map` 的键，改完之后再也查不到。
- 比较器不满足传递性时，排序结果不稳定甚至抛异常。
- 递归深度当成 O(log n) 的证明——退化输入会打爆栈。
- 优先队列按最小值出队这件事被反过来写成「先进先出」。
- 缓存淘汰只讲命中率，不讲淘汰时是否顺带丢了写回。

## 追问示例

- 「这个结构里最慢的一次操作是哪一步？它在这段代码里被调了几次？」
- 「如果同时插入两条 key 相同的记录，这里会覆盖还是报错？依据是哪一行？」
- 「这个缓存的容量上限在哪设的？淘汰掉的元素有没有需要落盘的？」

## 别讲什么

真实运行时的常数、缓存行与 CPU 局部性、GC 压力、并发下的实际性能——都看不到。能说出口的是「这里每次查询都会新建一个迭代器/复制一份列表」这种从代码结构直接得出的判断。
