# 流程图

先取 `project-visualization` 那份的六步流程；这一份只补流程图特有的证据与判据。

## 适用范围

回答「这个函数/这条链路怎么一步步走、在哪里分叉、什么条件下离开」。跨模块的**消息顺序**请用 `diagram-sequence`，模块构成用 `diagram-architecture`。

## 证据需求（按顺序取）

本仓有静态产物时走 1~3；没有（清单里没 `query_facts`，或它回「本仓还没有这类产物」）就直接走 4~5，用源码原文当依据，**不要因为这一步就走不下去**。

1. `query_facts { kind: "cfg", path: "<目标文件>" }` —— 先看这个文件里有哪些函数、各自圈复杂度多大，挑出真要画的那个。
2. `query_facts { kind: "cfg", path, target: "<函数名>" }` —— 展开成节点与边：`entry / branch / loop / selector / handler / exit / straight` 七类块，边类型 `next / true / false / back / exception / finally`。
3. `query_facts { kind: "dataflow", path, target }` —— 状态变化的依据：哪个变量在哪行被写、哪些行读到；「这里更新了什么」这句话由它支撑。
4. `read_file` —— 把 `if` 的条件、`switch` 的判据写成读者看得懂的话；产物只给了块与边的形状，语义在源码里。
5. 跨函数的流程：再对下游函数重复 1~2，或用上下文里的调用边确认「真的会调到它」。

## 语义建模规则

- **判定节点来自真 branch/selector 块**，不是你觉得这里有个分支。合并连续 `straight` 块成一个动作步骤（一次赋值 + 一次调用合成「算出 X」）。
- `loop` 块画成回边到自身的那一格，`back` 边就是循环体尾→条件；**别把循环画成线性三步**。
- `exception` 与 `finally` 边单独成一条离开路径，标注是异常/收尾，不并进主干。
- 每个 `exit` 块都要落到图的终点：没有 `return` 的函数（只 throw 或走到尾）也要有一个终点。
- 复杂度高（>10）的函数不要硬塞：画主干 + 一个「另有 N 处分支，见源码 行号区间」的说明节点，并告诉用户完整形状看哪几个块。

## 图形表达规范

真源是画布，`set_diagram` 的 `draw` 一次交整张。步骤节点用 `kind=note`（流程图不必绑模块 `ref`），判定用带问号的 label；分支的两条边把「是 / 否」或具体条件写在边的 `label` 上。文本 Mermaid 只作导出用，与画布同一份结构。

## 质量校验规则（回话前自查）

1. 图上的每个分叉都能指出依据：有产物时是 `cfg` 里的哪个块（记行号），没产物时是源码里那一句 `if` / `switch`（记文件与行号）。两者都给不出来的分支不画上。
2. 没有走不通的死路，也没有凭空多出的出口。
3. 每条边的条件来自源码原文，不是「大概是要检查参数」。
4. `truncated`（块数打满上限）或 `notes` 里「接不上」的那些，必须在回话里说明图不完整、缺什么。

## 证据限制（要如实交代给用户的）

- **静态可达路径 ≠ 每次执行都发生**。图上那条分支可能一辈子不走；不要写「系统会……」，写「当……时走到」。
- 函数内的定义与使用不跨函数：`unresolved` 里那些读不到定义的变量，多是参数、外层作用域或第三方对象，别断言是 bug。
- 带标签的 `break` / `continue`（Rust、Java、C#）目前按最内层循环接边；跨层跳出的图要看 `notes`。
- Python 的 `match/case`、`for/else` 不进控制流图；宏与生成代码在 `skipped` 里点名，那些函数根本没有图。
