# 数据结构与算法：可考的点

## 能摘出来考的（含替身怎么给）

| 考点 | 摘法 | 测试怎么断 |
| --- | --- | --- |
| 淘汰策略一步决策 | 摘「给定访问序列与容量，返回被淘汰的键」 | 断言被淘汰的键与剩余内容 |
| 比较器与排序稳定性 | 摘比较函数本身 | 断言多组两两比较结果，含相等、传递性反例 |
| 二分与边界 | 摘「找第一个满足条件的位置」 | 断言空数组、全满足、全不满足、重复值四种输入 |
| 分组聚合键的选取 | 摘「从记录算出分组键」 | 断言同组/不同组的归类结果 |
| 环形缓冲的读写指针 | 摘「算下一个写位置与是否满」 | 断言回绕、满、空三种状态 |
| 去重与键的一致性 | 摘「算哈希键」的函数 | 断言逻辑相等的两条记录算出同一个键 |

## 常见误解转成的缺陷

- 边界差一（`<=` 与 `<`、末位漏掉）——二分、分片、游标都是这一类。
- 可变对象当键之后又改它 → 断言查不到。
- 比较器不满足传递性 → 给三条记录断言排序结果稳定。
- 优先队列出队方向反了（要最大给了最小）→ 断言出队顺序。
- 用 `List.contains` 做成员判断导致线性开销 → 这类**不能**考性能，改考它在重复键下返回错结果。

## 不要出成题的

时间/空间复杂度的实测差异、缓存局部性、GC 压力、随机化快排的实际表现。考「算得对不对」，不考「跑得快不快」。

## 形状示例

- **好**：一个纯函数按「最近使用时间 + 容量」返回该淘汰哪个键，缺陷是漏了「刚插入就被访问」这一支；三条断言覆盖满、未满、全同时命中。
- **坏**：让学习者「把线性查找换成哈希查找」，然后断言耗时下降——判不了，也不改变任何返回值。
