# Go 语言特性：可考的点

## 能摘出来考的（含替身怎么给）

| 考点 | 摘法 | 测试怎么断 |
| --- | --- | --- |
| slice 共享底层数组 | 摘「把一段切片传出去后又被调用方修改」的函数 | 断言调用方改动不影响原切片（正确做法是 `append([]T(nil), s...)` 拷贝）；缺陷版直接传 `s[:k]`，改一个动全身 |
| `append` 后原切片是否联动 | 摘「往切片追加后又读原切片」 | 分两种容量造输入：容量够时共享（联动），扩容后不共享（不联动）；缺陷版假设其中一种，另一种必然错 |
| nil map 写入 | 摘「往 map 里累加结果」的方法 | 断言未初始化的 map 也能写（正确做法先 `make`）；缺陷版直接赋值，运行 panic |
| 接口值为 nil 但底层不为 nil | 摘「返回 `error` 或接口类型的函数」 | 断言失败路径返回的确实是 nil 接口（`if err != nil` 才成立）；缺陷版返回 `(*MyErr)(nil)`，判空为 false |
| `defer` 的参数求值时机 | 摘「defer 里读变量或打印状态」 | 断言 defer 执行时看到的是当时的值还是最终值；缺陷版以为 defer 会延迟求值 |
| 返回值被 `defer` 改写 | 摘「命名返回值 + defer 里改它」 | 断言最终返回的是 defer 改写后的值；缺陷版以为 defer 只是清理 |
| 错误被覆盖或漏检 | 摘「多步操作串起来」的编排函数 | 断言中间某步失败时整体返回该错误；缺陷版每步都 `err =`，最后只查一次 |
| `len` 与 `cap` 的误用 | 摘「按容量算边界」的逻辑 | 用刚好等于 len 与刚好小于 cap 的输入各断一次；缺陷版拿 cap 当已用长度 |
| 循环变量的地址 | 摘「把 `&item` 收进切片或 map」 | 断言收集到的是每个元素各自的值；缺陷版取到的是最后一次迭代的地址 |

## 常见误解转成的缺陷

- 「切片是引用类型」→ 传参确实共享底层数组，但 `append` 触发扩容后就断了；可考「哪里必须拷贝」。
- 「`nil` 切片不能 append」→ 可以；缺陷版多写了不必要的 `make`，或反过来对 `nil` 做下标赋值。
- 「`defer` 一定在 return 之后执行，改不了返回值」→ 命名返回值可以；可考「清理与返回值的顺序」。
- 「`time.After` 用完就没了」→ 每轮循环都建一个会泄漏计时器；可考「该用 `NewTimer` 并在循环里 Reset」。
- 「`map` 读不存在的键会报错」→ 返回零值，要用 `, ok` 形式；缺陷版把零值当"存在"。
- 「`switch` 会自动贯穿」→ Go 默认不贯穿，`fallthrough` 才贯穿；缺陷版把别处的习惯带过来。
- 「字符串切片是独立拷贝」→ `s[a:b]` 与原串共享底层数组；可考「大字符串里截一小段导致整串留驻」的规避。

## 不要出成题的

- `for range` 循环变量是否复用——**Go 1.22 起每次迭代都是新变量**，这个行为取决于工具链版本，换版本答案就变，不适合当考点。
- 真实并发下的 `race`、`select` 的随机性、goroutine 调度顺序——需要真并发与真时钟，沙箱里复现不了。
- `map` 的迭代顺序、哈希实现、扩容行为——刻意不确定，不能当"期望值"。
- GC、`GOGC`、内存占用、基准测试的 ns/op——与环境绑定，不属代码行为。
- 编译期行为（泛型实例化、内联、逃逸分析结果）——改了不改变运行结果。

## 写测试时的语言约定

测试文件与实现文件同属 `package main`，都放在根目录（不要建子目录）；**实现文件不得再定义 `func main`，main 只写在测试文件里**。每条断言用 `if` 分支计数（通过 `pass++`，失败 `fail++` 并把原因打到 stderr），结尾 `fmt.Printf("TESTS %d %d\n", pass, fail)`，`fail > 0` 时 `os.Exit(1)`。只用标准库；被测代码需要的仓库内符号，写成最小替身一起放进 `hidden`。
