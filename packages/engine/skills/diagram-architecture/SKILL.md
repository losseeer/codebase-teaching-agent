# 架构图

先取 `project-visualization` 那份的六步流程；这一份只补架构图特有的证据与判据。

## 适用范围

要回答「这个系统由哪几块组成、谁依赖谁、边界在哪」。不该用它回答「这个函数怎么走」（那是 `diagram-flow`）或「一次请求按什么顺序穿过谁」（那是 `diagram-sequence`）。

## 证据需求（按顺序取）

| 查什么 | 怎么查 | 用来定 |
| --- | --- | --- |
| 模块清单与分层 | 上下文里的项目结构全景（按目录分组的已分析文件） | 节点与它们的归属 |
| 模块之间的依赖方向 | 上下文里的依赖关系段（import 聚合） | 连线 |
| 谁实现了哪个接口 | `query_facts { kind: "typeRelations", path }` 或加 `target=类型名` 全仓找 | 边界处的真实落点（接口在 A 层、实现在 B 层） |
| 运行时才连上的关系 | `query_facts { kind: "registry", path/target }`：依赖注入绑定、路由登记、SPI 清单、构建清单的键 | 「A 通过容器拿到 B」这类边，import 图里根本没有 |
| 外部依赖 | 上下文里的「边界之外」那一份（包名清单） | 外框与云/库节点 |

## 语义建模规则

- **节点 = 模块，不是文件**。一个模块里有几十个文件时画一个节点，细节进 `sub`（一句话职责）。
- **分组按「变更原因」不按目录**：目录是物理布局，同一个目录里可以同时放着接入层与实现层。
- **边的方向 = 依赖方向**（谁引用谁），不是数据流方向，更不是执行顺序。这两个混淆是架构图最常见的错。
- **依赖注入边要写明是运行时的**：`sub` 里标「容器绑定」，读者才知道代码里没有那一行调用。
- 默认节点数 ≤ 12。超了就把同类的并进分组，别把图铺满屏。

## 图形表达规范

真源是画布：`set_diagram` 的 `draw` 一次交 `{groups, nodes, edges}`。`kind=module` 的节点**必须带真 `ref`**：`file:<路径>` / `dir:<目录>` / `symbol:<路径>#<符号>`，或 `group:<id>` 并附 `files` 清单；指不到索引就不落笔。用户要一份能贴进文档的文本图时，另给一段 Mermaid 作为**导出**，内容必须与画布那张同一份结构——两份图各说一套比没有图更糟。

## 质量校验规则（回话前自查）

1. 每个 `module` 节点都能说出一条依据：哪几条 import、哪一条 DI 绑定、或哪个路由登记。
2. 没有孤立节点（既不指人也不被人指）——通常是它根本不属于这张图要回答的问题。
3. 分层没有倒挂：被依赖的在下面。出现「上层指下层又指上层」时，说明有个节点其实是两个模块。
4. 每条边说得出类型：源码里的 import、类型关系、还是容器绑定。三者混成一种就等于没说。

## 证据限制（要如实交代给用户的）

- 反射、按约定加载的插件、动态 import 不产生边；图上少一条线不代表运行时无这条线。
- `query_facts` 里带 `同名多解` 的边不能挑一个落点当事实，要说「这两个文件里都有这个名字」。
- 标准库与第三方类型反查不到仓内文件（边留着但没有落点），这不是「不存在」。
