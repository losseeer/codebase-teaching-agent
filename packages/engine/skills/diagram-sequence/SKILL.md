# 时序图

先取 `project-visualization` 那份的六步流程；这一份只补时序图特有的证据与判据。

## 适用范围

回答「一次请求/一个动作穿过哪几个角色」。单个函数内部的分叉用 `diagram-flow`；模块构成用 `diagram-architecture`。

## 证据需求（按顺序取）

1. **起点**：入口从上下文里那份入口清单取（路由、`main`、脚本守卫），不要自己挑一个文件当起点。
2. **调用边**：上下文里那个文件的依赖关系段（含二度邻接）与 `read_file` 的实证——**每条消息都要能指出「谁在哪一行调到谁」**。
3. **参与者是谁**：`query_facts { kind: "typeRelations", target: "<接口名>" }` 把「控制器 → 服务接口」落到「实现类在哪个文件」；接口和实现是两个参与者，画成一个会把职责说糊。
4. **运行时才连上的那一跳**：`query_facts { kind: "registry", target: "<接口名>" }` 看依赖注入绑定、SPI 清单、路由登记。这类边在 import 图里不存在，只有这里能给。
5. **数据流（可选）**：`kind: "dataflow"` 用来确认「这条消息带的值从哪来」，别用它推断顺序。

## 语义建模规则

- 参与者 = 有职责的角色（控制器 / 服务 / 缓存 / 数据库 / 外部服务），不是每个类一个。
- 消息方向 = 调用方向。返回值可以画一条虚的回程，但**没有依据就不要画**（静态证据只给了「调到了」）。
- 一条链路上出现「接口 → 实现」时，用注册索引那条边来断定实现是谁；断定不了就把参与者写成接口并注明「实现有多个」。

## 图形表达规范

真源是画布：`set_diagram` 的 `draw` 一次交 `{groups, nodes, edges}`，节点是参与者（能对上模块就给 `ref`），边按消息方向画并把方法名写在 `label`。**画布没有「时间轴」这一维**，所以序号要写在 label 里（`1. 校验`、`2. 查缓存`…），别指望布局自动表达顺序。需要文本图时另给 Mermaid 作为导出，结构与画布一致。

## 质量校验规则（回话前自查）

1. 每条消息都说得出出处：`文件:行号` 或产物里那条注册/类型边。
2. 参与者的编号连续，且第 1 条消息真的由入口发出。
3. 回程/返回不超过有依据的那几条。
4. 图上出现的每个「异步」「事件」字样都能指出证据（源码里真有 `async`/回调/发布订阅），否则改成同步措辞。

## 证据限制（这一格最重要，别跳）

- **静态分析给不出真实执行顺序**。调用边只说明「A 会调到 B」，谁先谁后、是否并发、回调何时触发都不在这些产物里。顺序只能从源码里那一次具体调用读出来；读不出就把那条消息标「顺序未证实」，不要按字母序或按文件顺序凑一条线。
- 异步与事件驱动（消息队列、监听器、`@Async`、`go func()`、Promise/协程）的派发是运行时的：产物里最多看到「注册了一个处理器」，看不到「什么时候触发」。
- 反射、动态代理、宏展开不产生边；`registry` 里配置文件只有键名没有值，所以「用哪个地址连哪台库」这类结论这里给不了，要读源码或问用户。
- `dataflow` 是函数内的：跨过程「这个值被谁改过」不在这张表里，别拿它当数据流图。
