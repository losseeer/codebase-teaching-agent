# 项目可视化（通用流程）

用户要求画架构图 / 流程图 / 时序图时按本流程执行。改图只在架构全景工作区可用（该工作区提供 `set_diagram`）；代码问答与练习两个工作区没有该工具，不做改图尝试。

## 六步

1. **先问清三件事**：图类型（架构 / 流程 / 时序）、目标范围（模块、文件或入口）、表达目标（给谁看、说明哪一件事；图的详略由此决定）。三项缺两件以上时先向用户确认，再动手。
2. **取对应的专用技能**：`read_skill` 读取 `diagram-architecture` / `diagram-flow` / `diagram-sequence`，以其「证据需求」决定下一步查什么；未读正文即连线，属于无依据作图。
3. **查产物在册情况**：`query_facts` 不带参数调用一次，得到 `cfg` / `dataflow` / `typeRelations` / `registry` 四类产物的覆盖范围与计算时间；此趟只查在册情况，不取内容。四类分别是：`cfg`（函数内控制流）、`dataflow`（变量读写链）、`typeRelations`（类型关系边）、`registry`（注册与构建清单）。工具不存在或返回「本仓库还没有静态产物」时，按「产物缺失时的替代路径」继续，不中断回合。
4. **按证据需求取读数**：一次一个指针（`kind` + `path`，必要时加 `target`）。产物是仓库级确定性重算的结果，不因查询而重算，也不由绘图方重算。
5. **语义读源码**：产物只回答「结构上谁连着谁」；职责、业务含义、分层原因用 `read_file` 取，找不到文件先 `search_code`。读三五个文件即可，不读入整个仓库。
6. **一次交付整张图**：`set_diagram` 的 `draw` 动作提交完整 `body={groups,nodes,edges}`，不逐格试写。**重画一张已经存在的图必须带 `diagram`（id 或名字）**：带目标 = 整张替换、上一版进版本历史；不带目标 = 新建一张，重复调 `draw` 会多出一张同名「（2）」。提交后按专用技能的「质量校验」自查，再回复用户。

## set_diagram

动作、字段与 `ref` 规则以工具内 `action=help` 的返回为准；第一次改图前先取一次。`origin` 只填 `static` 或 `code`，引擎核不到会降为 `inferred`；不要自行填写 `inferred` 或 `downgraded`。

## 产物缺失时的替代路径

- 不在绘图过程中重新运行静态分析；产物缺失时向用户说明缺什么，是否重新分析由用户决定。
- 产物缺失不阻断本轮交付：以 `read_file` 读到的源码原文为依据作图，边的证据档位相应为 `code`（读过两端文件的正文）或 `inferred`（仅知调用关系）；未读到分支条件的不画分叉，画为顺序路径并注明「存在未核实的分支」。

## 证据完整性

- 静态产物查不到的关系（动态派发、反射、异步事件、条件顺序）一律标「未证实」并说明原因，不构造看似合理的边。
- `set_diagram` 的 `origin` 字段由引擎按三张结构表逐条核验，核不到自动降为 `inferred`；如实申报所依据的证据类别，不自行填写 `inferred` 规避核验。

## 回话方式

- 主干存在取舍时，先交付已核实的主干图，再询问是否补充分支或更换主干；只有范围完全未定（三项缺两件以上）时才允许暂不出图。
- 回话包含三项：画了什么（对应这张图要回答的问题）、依据来自哪里（产物 / 源码）、未画哪些及原因。
