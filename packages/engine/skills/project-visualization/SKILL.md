# 项目可视化（通用流程）

**什么时候用**：用户要「画一张……图」「把这个模块的结构画出来」「这条链路怎么走」。
**适用范围**：只有宏观设计作用域能改图（那里才有 `set_diagram`）；教学与练习两张脸没有这个工具，别试图改。

## 六步

1. **问清三件事再动手**：图类型（架构 / 流程 / 时序）、目标范围（哪个模块、哪些文件、哪条入口）、表达目标（给谁看、要说清哪一件事）。三件里缺两件以上就回一句问，别猜——范围猜错的图，用户要重画。
2. **取对应那份专用技能**：`read_skill` 填 `diagram-architecture` / `diagram-flow` / `diagram-sequence`。它的「证据需求」决定你下一步查什么，不取正文就开画等于凭印象连线。
3. **先看有什么**：`query_facts` 不带参数调一次，回的是四类产物（`cfg` / `dataflow` / `typeRelations` / `registry`）各覆盖多少文件、算于何时。**这一趟不查内容，只查在册情况**——跳过它会让你后面每查一次才知道缺一次。清单里没有这扇门、或它回「本仓还没有静态产物」时，**直接换替代路径继续**（第 5 步的 `read_file` 与上下文里的调用边），别停下来等设备：这个仓只是在产物层落地之前导入的，图照样能画。
4. **按证据需求取读数**：一次一个指针（`kind` + `path`，必要时加 `target`）。产物是整仓级确定性重算的结果，不会因为你查了就重算，也不该由你重算。
5. **要语义就读源码**：产物只回答「结构上谁连着谁」，职责、业务含义、为什么这么分必须靠 `read_file`（找不到文件先 `search_code`）。读三五个文件就够，不要把整仓读进上下文。
6. **一次交整张图**：`set_diagram` 的 `draw` 动作给全 `body={groups,nodes,edges}`，不要一格一格试（每试一次都是一条新版本进图库）。写完按专用那份的「质量校验」自查一遍再回话。

## 三条红线

- **不在绘图过程中重新分析**：产物缺（`query_facts` 回「本仓还没有 xx 这类产物」）就把这句话原样告诉用户，请他重新分析。自己想办法「绕过去算一遍」是不存在的通道。**但产物缺不等于这轮不能交付**：改用 `read_file` 读到的源码原文当依据照样能画，只是边的档位只能到 `code`（你读过那两个文件的正文）或 `inferred`（只知道谁调用谁），分叉没读到条件就不画分叉、画成一条顺序路径并注明「这里有未核到的分支」。
- **查不到不等于没有**：动态派发、反射、宏、异步事件、条件顺序都不在静态产物里。这类关系只能标「未证实」并说明为什么，**不能编一条看着合理的边**。`set_diagram` 的 `origin` 引擎会拿三张结构表逐条核，核不到自动降成 `inferred`——所以照实报你依据的是哪一类证据，别试图自己填 `inferred` 蒙过核验。
- **抽象层级由图的用途决定**：架构图的节点是模块，不是文件；流程图的主干不超过十来个步骤。全量罗列等于没画——读者从图上得不到判断。

## 证据不够时的说法

**先交图，再问。**「要画哪条线为主干」这类取舍问题不该单独占一轮：先把已经核得到的那条主干画进画布（一张只含顺序步骤与已读分叉的图，比一段免责声明有用），再在回话里问要不要往下补分支或换主干。只有一种情况允许不落笔：范围完全没定（图类型、目标文件、入口三件里缺两件以上）。

回用户一段话，含三件：画了哪些（每张图要回答的那一个问题）、依据来自哪（产物 / 源码 / 都是猜）、没画哪些以及为什么。宁可交一张小图 + 一句「这一段没证据」，也不要交一张大话。
